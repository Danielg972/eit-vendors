## 1. What this project is, in one paragraph

The project is a free, invite-only web app where about 50 outside colleagues (licensed guides, travel agents and tour operators) share supplier information. That includes hotels, guides, transport, sites, national parks, restaurants and adventure operators. Members add prices, deals, notes, quotes, files and food tips. Eretz Israel Tours (EIT) approves members and controls the shared "truth" fields. It can export approved suppliers in the vendor-import format of the frozen EIT builder **R5**. The app lives at **https://vendors.eretzisraeltours.com**. It is **separate from the EIT Builder / Cockpit software program**. It does not read, write or deploy anything in eit-builder, eit-cockpit or the R5 file.

## 3. Architecture and security model

- **No passwords.** Each member has a personal link containing a random token. Only the SHA-256 hash of the token is stored, in `members.token_hash`. The token is kept in the browser's localStorage (key `eitv_link`).
- **All data access goes through `SECURITY DEFINER` RPCs that take `p_token`.** Row-level security is on for every table, and direct table grants to `anon` and `authenticated` are revoked. Each RPC calls `_auth(p_token[, admin])`. Admin is a member with `is_admin = true` (Eretz Israel Tours).
- **Locked "truth" fields** are name, category, status, contact details, the main price, cancellation terms and the park booking link. A non-admin edit to these becomes a `change_requests` row, which the admin approves or rejects in the Review tab. Other fields save straight away.
- **Private data:**
  - The admin can see everything, and the terms disclose this.
  - Price lines can be private (admin-only) or personal (only the owner and the admin see them).
  - A whole supplier's prices can be made private.
  - Files can be marked "only me and EIT".
  - Each supplier has an admin-only private note in `vendor_admin_notes`.
- **Colleague privacy pass (1 Oct 2026).** Non-admins never receive other members' emails, phone numbers or license numbers; names only. This was tested by creating a temporary non-admin member, calling every read RPC for every visible supplier, and scanning the output. The test was rolled back. Zero hits.
- **Imports stay hidden.** Anything imported by Claude is created with `hidden = true` and `review_status = 'pending'` until the admin approves it.

**Tables (19):** `action_log`, `app_settings`, `change_requests`, `contributors` (legacy), `feedback`, `filter_log`, `members`, `quote_lines`, `quote_options`, `quotes`, `reservation_reports`, `vendor_admin_notes`, `vendor_deals`, `vendor_files`, `vendor_food`, `vendor_notes`, `vendor_prices`, `vendor_reports`, `vendors`.

**Public RPCs (49):** `whoami`, `request_access`, `accept_terms`, `vendors_list`, `vendor_detail`, `vendor_save`, `price_save`, `deal_add`, `note_add`, `quote_save`, `food_add`, `report_vendor`, `vendor_set_agent`, `log_action`, `log_filter`, `my_top`, `my_usage`, and others. Admin-only RPCs: `members_list`, `member_decide`, `requests_list`, `request_decide`, `vendor_reports_list`, `activity`, `set_setting`, `vendor_set_status`, `vendor_delete`, and others.

**Finding fixed during this audit.** While writing the audit I found that three tables (`vendors`, `vendor_files`, `contributors`) still had grants to the `authenticated` role and 11 row-level-security policies left over from the first design, which used Supabase email login before the token system. They were unused (Supabase Auth has 0 users) but meant that someone who signed up through Supabase Auth with a member's confirmed email could, in theory, have read or written those tables directly. On 1 Oct 2026 I dropped the policies and revoked the grants (migration `drop_legacy_auth_policies`). Grants to anon/authenticated and public policies are now both **0**. The live app was re-checked afterwards and loads all 83 suppliers.

## 4. Features as of 1 Oct 2026 (what a member can do)

- **Joining**
  - Join form with role and optional license number. A duplicate license number is refused.
  - Photo of license as proof, or an opt-out ("can't add proof now") that requires an explanation.
  - Terms checkbox. The admin approves each request, and the member gets a personal link.
- **Finding suppliers**
  - Search with suggestions; category and region chips.
  - Chips are ordered by each member's own use. The list order is a "Mixed" daily shuffle per member, so no supplier sits on top because of its alphabetical position. An A–Z toggle is available.
  - A "Your most used" strip shows each member's favourites.
- **Categories**
  - Hotel, Guide, Transport, Restaurant, Attraction / Site, Activity, Adventure, National Parks, Travel Agent, Itinerary Planner, Flight, Other.
  - "Also offers" lets one supplier appear in several categories. The main category is the one exported to R5.
  - Form fields that don't fit the chosen category are hidden.
- **Guides.** Tags Eshkol license, Owns an Eshkol vehicle, Midbari 4x4 vehicle and Carries a gun can be used as filters. Years guiding is a separate field.
- **National Parks.** The authority is a parent supplier with each site under it. A one-time "did they make you reserve?" pop-up feeds reservation reports.
- **Contact buttons.** Call, WhatsApp, Email (with BCC to `suppliers@`, explainer pop-up, per-member opt-out), Website, Waze and Maps. Every outbound tap is logged in `action_log` (admin "Activity" view).
- **Prices**
  - Prices are optional. Multiple price lines per supplier (adult, child with ages, Israeli senior, group, vehicle and so on).
  - "Free" option.
  - Colleagues' personal prices, and private prices for the admin.
  - Clear "From [name]" attribution on anything a colleague adds.
- **Deals, notes and quotes**
  - Deals (Cal, Cuponofesh, codes).
  - Colleague notes.
  - Quotes with options shown as tabs, such as room types or midibus vs coach.
- **Agent prices box.** An agent sign-up link and how-to per supplier. "Ask for agent prices" sends a ready Hebrew or English WhatsApp or email that does not mention the list.
- **Files**
  - Photos, receipts, price lists, booking confirmations, contracts and kosher certificates.
  - A black-out editor that flattens the result to JPG or PDF before upload.
  - Private-file option.
- **Kosher.** Quick-pick kashrut levels and a kosher certificate photo.
- **Food nearby.** A folded section of colleague food tips per supplier.
- **Red "Update this supplier" button.** Report a supplier as closed or moved, contact changed, prices changed, a mistake, or other. Can be sent anonymously: the name is hidden even from the admin's list but kept in the database for rule enforcement.
- **Disclaimers and reminders**
  - A crowdsourced, no-responsibility disclaimer on every supplier page.
  - A monthly "colleagues only, never show suppliers" reminder.
  - Terms version `2026-10-01e`. This is a draft that a lawyer has not reviewed. It includes objective-feedback and no-slander rules.
- **Admin tabs**
  - **Review:** supplier updates, feedback, suggested changes, new suppliers, and "Build R5 import file".
  - **Team:** invite link, BCC address, join requests with proof, members, activity.

## 6. How the work was done (process facts the other project should know)

- **Testing**
  - Every front-end change was syntax-checked and exercised in headless Chromium (Playwright) against DEMO mode.
  - Database changes were checked with SQL, and sometimes with a rolled-back probe as described in section 3.
  - Live checks were done in Daniel's Chrome through the Claude-in-Chrome extension: fetching the deployed page and confirming new code is present, and reading the admin view.
  - **There is no automated test suite and no CI beyond the keep-alive.**
- **Releases.** Every change is committed straight to `main` and pushed; GitHub Pages deploys within about a minute. There is no review gate, no freeze record, and nothing like the CP or EW change process. That was deliberate: this is a small, fast colleague tool, not the governed EIT Builder.
- **Schema changes** were applied with Supabase `apply_migration` or `execute_sql` directly on the live project. **Migrations are not stored in the repo.** The database itself, through its Supabase migration history, is the record.
- **Permission events, recorded honestly**
  - Daniel explicitly authorized: creating the GitHub repo, clicking "Create repository", creating the email forwarder, and publishing.
  - An automated safety check **refused** pushing a kosher-certificate photo into the public repo as a stopgap file host. That workaround was dropped. Instead, an "Add kosher certificate photo" button was added so Daniel uploads it himself.
  - Earlier, an attempt to explore a stored GitHub token was also refused, and was replaced by the official add-repo flow.
- **Owner conventions applied**
  - Never call the owner "Daniel" in the app; use "Eretz Israel Tours".
  - Never modify R5.
  - Don't make Daniel carry files between sessions; use the repo and Project docs.
  - Write conventions into skills and prompts rather than relying on memory.

## 7. Known risks and open items (ranked)

1. **The terms are not lawyer-reviewed.** They cover tracking of taps, BCC copies, admin visibility, a slander ban and a no-responsibility disclaimer. They need Israeli legal review before wider rollout.
2. **The R5 export has not been round-tripped into R5.** The format was built from the R5 import audit (`_exportFormatVersion: 3`, `_tripVendors`, `days: []`, R5's 33 field keys, category mapping for new categories). It has not been imported into a real R5 instance. Importing blanks the current trip view, which is the known R5 behaviour. IDs do not yet match Daniel's existing R5 vendor IDs; this needs an R5 vendor export from Daniel.
3. **Unverified imported data.** 41 hidden suppliers wait for Daniel's review. Old-sheet prices are years old.
4. **Keep-alive might not keep the database awake.** The workflow calls `/rest/v1/vendors` with the publishable key, but direct table access is revoked, so the call probably returns 401 or empty. Whether a rejected REST call counts as activity for Supabase's free-tier pause rule is **unverified**. A safer ping would call a harmless RPC.
5. **Schema is not in the repo.** Disaster recovery depends on Supabase. There is no exported SQL dump or migration folder.
6. **Free-tier limits.** Supabase free: 500 MB database, 1 GB storage, and the project pauses after inactivity. GitHub Pages: the repo is public. The source contains no secrets beyond the publishable key, which is meant to be public, and the service key lives only in the edge-function environment.
7. **Single-file front end.** About 1,760 lines in one file. Easy to deploy, but harder for another AI to review in one pass.
8. **Privacy and tracking.** Contact taps are logged per member and emails are BCC'd unless the member opts out. Both are disclosed in the terms. Anonymous reports keep the author in the database.
9. **The colleagues-only rule** ("never show suppliers") is enforced only by the terms and the reminder. There is no technical way to prevent screenshots.

## 9. How another session can verify this audit

1. **Code.** `git clone https://github.com/Danielg972/eit-vendors`, then `git log --oneline`, then read `index.html` and `README.md`. Check that this file's commit SHA matches the one cited.
2. **Database.** Use the Supabase connector on project `wjuqtjlrtcywjaspjpwu`:
   - `list_tables`
   - `select proname from pg_proc where pronamespace='public'::regnamespace`
   - Confirm RLS is on for every table, that `anon` and `authenticated` have no table grants (`select grantee, table_name from information_schema.role_table_grants where table_schema='public' and grantee in ('anon','authenticated')` should return nothing), and that `select count(*) from pg_policies where schemaname='public'` returns 0.
3. **Privacy claim.** Re-run the rolled-back non-admin probe (create a temporary approved member, call the read RPCs, scan for member emails, phones and licenses, then raise to roll back).
4. **Live site.** Open the URL. Off-domain previews show DEMO mode.
5. **Edge function.** Supabase `get_edge_function files` (v8).

## 10. Skills or rules the other project might write for this one

- **`suppliers-list-steward`.** Status check: pending reviews, supplier updates, feedback, join requests, last keep-alive success, free-tier usage, terms version. It should answer "what needs Eretz Israel Tours this week?" without building anything.
- **`suppliers-list-import`.** House rules for bringing data in: hidden + pending, an "unverified" line, old prices private, sources and client context only in admin notes, dedupe by `normN(name)` and phone, and never put client names in visible fields.
- **`suppliers-list-change-rules`.** For any AI changing the app:
  - Never call the owner "Daniel".
  - Never modify R5.
  - All data access through token RPCs; never grant direct table access.
  - Bump `TERMS_VERSION` when the terms change.
  - Keep "From [name]" attribution.
  - Never return member emails, phones or licenses to non-admins.
  - Test in DEMO mode and with a non-admin probe.
  - Update the README and Project doc after each change.
- **`suppliers-to-r5-export`.** The exact mapping and the checks to run before importing into R5: back up first, expect the trip view to blank, and match IDs.
